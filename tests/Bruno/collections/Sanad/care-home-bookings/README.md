# Care-home booking coverage

This collection is an ordered, stateful contract suite for HC-TASK-032. It is authored for the disposable Development Paymob fixture only; it must not contact Paymob or any production endpoint.

Prerequisites are an approved facility, active room type and inventory, a family owner with an eligible elderly dependent, an effective Finance charge rule, a care-home owner for the facility, and `fixtureHmacSecret` in `local-fixtures`. Record fixture identities before runtime. Requests may create their documented booking/payment/case state, but no request resets or drops the database.

The first three booking prerequisites are replay-safe readbacks, inserted after request `02-checkout-validation`: `02a-read-family-dependent.bru` calls `GET /api/v1/family/dependents` and stores the first dependent as `careHomeElderlyId`; `02b-read-discovery-fixture.bru` calls the public discovery list and stores the approved facility as `careHomeFacilityId`; `02c-read-discovery-room-type.bru` reads that facility detail, stores its first active room type as `careHomeRoomTypeId`, and derives a start date 60 days ahead as `careHomeStartDate` unless an explicit ISO `careHomeStartDate` environment value is set for a non-overlapping fixture. Set optional `careHomeExpectedFacilityId` and `careHomeExpectedRoomTypeId` in the environment when more than one eligible facility or room type exists; the readbacks then fail closed if that exact identity is absent. These reads do not create, mutate, reserve, or clean up state.

For HC-032 runs, the selected `local-fixtures` environment must provide `baseUrl`, `appEnvironment=Development`, family/owner credentials, and `fixtureHmacSecret`; response scripts derive transaction ID, amount, merchant reference and HMAC from actual responses. Do not hard-code these values. If required configuration is absent, stop and report it; do not run a fixture helper or replay onboarding without exact owner authorization. The HC-034 run recorded below reused the existing environment with explicit `--env-var` overrides and `baseUrl=http://localhost:5235`; no fixture helper was used.

The API keeps the production timing contract in every environment unless the disposable local API explicitly enables the Development test clock: checkout hold 15 minutes, paid decision hold 24 hours, earliest arrival 24 hours, and expiry sweep 1 minute. To avoid waiting during the two timeout scenarios, start the already-pinned local Development API with `CareHomes:TestClock:Enabled=true` and positive values for `CareHomes:TestClock:CheckoutHoldDuration`, `CareHomes:TestClock:DecisionHoldDuration`, and `CareHomes:TestClock:ExpirySweepInterval` (for example 30 seconds, 1 minute, and 5 seconds). Do not set or invent an `ArrivalLeadDuration` override; it remains 24 hours. There is no public test-control endpoint, and the guard rejects overrides without `Enabled=true`, enabled test clocks outside Development, and non-positive durations. Keep the same fixture identity and follow the Bruno failure-first runbook; this timing shortcut does not authorize a reset, onboarding replay, or production use.

The legacy HC-032 requests currently occupy unique contiguous `meta.seq` values 0–33. The HC-034 manifest below occupies 34–64. Run explicit paths in the required sequence with the pinned local environment and `--bail`; do not run the entire folder as one stateful scenario because the extended one-time cases require separate fixtures.

The suite also includes `15-family-unauthenticated.bru` (401) and `16-owner-state-conflict-after-rejection.bru` (409). A separate disposable run is required for checkout-hold expiry, the 24-hour decision timeout, acceptance, payment failure, shared-bed versus private/suite capacity, maintenance overlap, duplicate/current holds, and two concurrent last-capacity checkouts. Those cases are one-time stateful scenarios and cannot safely be replayed against one fixture. Cleanup is readback only because HC-035 owns cancellation/refund recovery and no destructive fixture endpoint is authorized here.

Replay classification: login/list/detail/negative reads are replay-safe; checkout, payment intent, signed success/failure callback, owner decision and concurrency requests are one-time and require a fresh disposable fixture or an unused inventory slot.

Extended one-time scenarios:

- `17-webhook-payment-failure.bru` checks a signed failed callback; `17a-payment-failure-readback.bru` verifies the booking is Cancelled/Failed. The callback's transaction, amount, merchant reference, and HMAC are derived from the actual payment-intent response by `05-payment-intent.bru`.
- `18-owner-accept-separate-fixture.bru` accepts the newest separately paid booking (HTTP 200 with the returned booking DTO); `18a-owner-accept-readback.bru` verifies Accepted/Paid. Do not run after the rejection flow.
- `19-checkout-hold-expiry-readback.bru` requires a booking created at least 15 minutes earlier, or a Development test-clock fixture with a short positive checkout hold and sweep interval, and expects Expired. When using a short fixture duration, pass `--env-var careHomeCheckoutExpiryWaitMs=<hold milliseconds plus sweep margin>` so the request waits only for that test deadline; omit it when the fixture is already expired.
- `20-decision-timeout-refund-readback.bru` requires verified payment older than 24 hours, or a Development test-clock fixture with a short positive decision hold and sweep interval. Pass `--env-var careHomeDecisionExpiryWaitMs=<decision milliseconds plus sweep margin>` for the bounded Development wait. The hosted expiry sweep claims the refund and the Development Paymob stub completes it, so the final readback expects `RefundInitiated = 8` and `PaymentStatus = RefundInitiated = 4` (not the intermediate `RefundPending = 7`).
- `21-shared-capacity.bru`, `22-private-suite-capacity.bru`, and `23-maintenance-overlap.bru` require dedicated inventory fixtures; shared capacity is bed-based, private/suite capacity is room-based, and maintenance overlap must return CapacityConflict.
- `24-overlapping-last-capacity-a.bru` and `25-overlapping-last-capacity-b.bru` must be dispatched concurrently from separate Bruno processes against one disposable fixture. The approved result is exactly one 200 and one 409; sequential execution does not prove the PostgreSQL advisory-lock race.
- `26-family-cross-family-safe-not-found.bru` and `27-owner-cross-facility-safe-not-found.bru` require entities owned by another family/facility and expect privacy-preserving 404 responses.

The timeout cases are not runnable with ordinary wall-clock sequencing; use the documented Development test-clock configuration for short local runs. Never edit timestamps or reset the database to force them. Payment failure, acceptance, maintenance, capacity and concurrency cases each use separate one-time fixtures. Booking/fixture cleanup is retention plus readback; request 86 is only an exact Owner-session revocation and does not delete fixture records.
